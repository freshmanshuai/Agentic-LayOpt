# Electronic-control equipment workshop

This is the only published case example. It preserves an actual Agentic LayOpt workbench session.

The inputs were prewritten natural-language requirements submitted through the ordinary workbench. DeepSeek performed linguistic slot extraction and engineering-grounded intent understanding before the general task compilation, execution, validation, and recovery steps.

## View the recorded result

From the repository root:

```sh
python -m tool.api.rough_design_api_server --recording-only --workspace-snapshot examples/electronics_workshop/stages/repair/workspace.json
```

This mode serves the saved result and included models. It does not initialize inference clients, call DeepSeek, build an index, run a solver, or create a new verification receipt. The input and Send controls are disabled. Recorded receipts remain historical evidence.

To inspect another stage, restart with `stages/generate/workspace.json`, `stages/optimize/workspace.json`, or `stages/edit/workspace.json` instead. The layouts are taken from the captured viewport commands, not regenerated by a case-specific algorithm.

## Run new requests

Start the normal server without `--recording-only`, using your own provider configuration and retrieval index as described in the root README. Open the ordinary workbench at `/`. Paste `inputs/engineering_context.txt` into the engineering-context field and submit `inputs/turn-01.txt` as the initial request.

Respond to the new run's actual clarification choices. The remaining text files show the historical prompts and operator reply, not an instruction to inject those replies automatically into a different run. Optimize, Edit, and Repair should operate on that new run's accepted states. A new run produces its own outputs; this recording does not establish that new outputs or timings will be identical.

## Preserved sequence

The business session is recorded from 2026-10-19 05:59 to 07:04 UTC.

| Turn | Operation | Recorded status | Role in the example |
|---|---|---|---|
| 1 | Generate request | Needs clarification | Retained |
| 2 | Operator clarification | Valid solver-ready | Selected Generate result |
| 3 | Optimize | Valid solver-ready | Selected Optimize result |
| 4 | Edit request | Needs clarification | Retained |
| 5 | Edit continuation | Valid with warnings | Proposal rejected during review; retained as history |
| 6 | Edit retry | Valid with warnings | Selected feasible alternative |
| 7 | Repair | Valid solver-ready | Selected Repair result |

Generate and Optimize came from the initial accepted run. The later continuation restored those accepted states before producing the selected Edit and Repair. This is an interactive development session, not one uninterrupted, intervention-free run. Earlier development attempts outside this business session remain private.

The operator clarification in turn 2 was supplied by the assistant operator using recorded candidate choices and prior user authorization. The compiler also applied deterministic normalization and binding rules. Existing grounding was reused where recorded; not every turn performed a fresh retrieval.

The final Edit did **not** exactly satisfy the original directive. Its disclosed feasible alternative displaced two objects from the requested endpoints by approximately 1.1613 m and 3.3987 m. See `results/edit_deviations.json`. 
## Files and evidence

- `inputs/`: the actual engineering context and all seven submitted texts.
- `recording/requests/`: submitted JSON bodies, without browser transport headers.
- `recording/llm_calls/`: 14 original intent-understanding request/response records, copied verbatim. Requests name `deepseek-v4-flash`; response model fields say `deepseek-flash`.
- `recording/events/`: five original SSE response bodies and two captured UI traces. Standalone HTTP bodies were not captured for the two clarification turns; their filenames and `recording.json` disclose the distinction.
- `stages/`: the four accepted layouts, extracted FLP-IR records, and workbench-view snapshots. Layout identity, positions, rotations, and dimensions match the recorded viewport commands.
- `results/`: recorded measurements, outcomes, material flows, equipment changes, and Edit deviation disclosure. These are the selected example's historical results, not new benchmark measurements.
- `recording.json`: sequence, evidence references, selected turns, and limitations.

Local absolute paths, browser transport headers, private server-control files, and screenshots are not distributed. The measurements file omits only its local `source_run` path. Original inputs, model request/response records, event content, stage outcomes, and numerical values are otherwise preserved as described above. No new benchmark version, hash, or frozen result set is introduced.
